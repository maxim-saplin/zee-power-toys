**Notes on choices:**

- `hooks_riverpod` (not bare `flutter_riverpod`) is chosen because the project already decided to use `flutter_hooks` for widget-local boilerplate reduction (ADR 0006 explicitly says "adopt it where it reduces `StatefulWidget` boilerplate"). `hooks_riverpod` re-exports both.

- No `bloc` / `provider` / `signals` — ADR 0006 explicitly rejects them as primary; Riverpod is the single primary.
- No Hive — ConfigStore must be native-readable (ADR 0003:14); `shared_preferences` stores plain prefs.

### Derived state — stream → view model

```dart
// lib/providers/car_signals.dart
final carSignalEventsProvider = StreamProvider<CarSignalEvent>((ref) {
  return ref.watch(carSignalsProvider).events;
});

// Specific derived values
final speedProvider = Provider<int?>((ref) {
  final event = ref.watch(carSignalEventsProvider).valueOrNull;
  return event is SpeedEvent ? event.speedKmh : null;
});

final blinkerProvider = Provider<BlinkerState>((ref) {
  final event = ref.watch(carSignalEventsProvider).valueOrNull;
  return event is BlinkerEvent ? event.state : BlinkerState.off;
});
```

### Per-isolate containers

Each isolate (`main.dart` and `main_hud.dart`) creates its own `ProviderScope` / `ProviderContainer`. They never share a container — cross-isolate events flow via the native relay (ADR 0003). ## 6. Testing Approach

### Guiding philosophy (from `/home/user/src/zee-power-toys/.agents/skills/tdd/SKILL.md`)

- Tests verify behaviour through public interfaces, not implementation details.
- Vertical slices via tracer bullets: one test → one implementation → repeat.
- Tests describe WHAT the system does, not HOW it does it.
- A good test survives internal refactors.

### Directory structure (mirror `lib/`)

```
test/
  models/          # unit tests for data classes
  services/        # unit tests for service ports (mock the transport-level)
    mock_car_signals.dart    # implements CarSignals; controllable stream
    mock_config_store.dart   # implements ConfigStore; in-memory
  providers/       # Riverpod provider unit tests using ProviderContainer directly
  widgets/         # widget tests with MaterialApp wrapper + ProviderScope.overrides
  screens/         # full-screen widget tests
  support/
    pump_until.dart   # async polling helper (port from nothingness)
integration_test/    # cross-widget behavior on emulator/device (T2+)
dev/                 # out-of-tree harness — NEVER imported by lib/
```

### What to mock

Mock only at **system boundaries** (ADR 0002 ports):
- `CarSignals` — mock the abstract port, not the native bridge
- `ConfigStore` — an in-memory implementation is sufficient for most tests
- `MinimapHost` / `HudHost` — stub commands, emit controllable events
- Platform channels (use `TestDefaultBinaryMessengerBinding.instance.defaultBinaryMessenger.setMockMethodCallHandler`)

Do NOT mock:
- Internal Riverpod providers
- Data model helpers
- Pure computation functions

### Mock/fake pattern (from nothingness)

Two variants used in nothingness (`test/services/mock_audio_transport.dart`, `dev/fake_audio_transport.dart`):

1. **`MockXxx`** — lives in `test/services/`; manually-written `implements` class with call-tracking lists (`loadCalls`, `pauseCalls`, etc.) and configurable failure modes (`pathsToFailOnLoad`). Used in unit tests where call verification matters.

2. **`FakeXxx`** — lives in `dev/`; cleaner, outcome-map-based implementation (`outcomesByPath: Map<String, FakeLoadOutcome>`). Used in integration tests via `dev/main_test.dart`. No call-tracking, just deterministic behavior.

For zee-power-toys, the same two-variant pattern applies per service port:
- `test/services/mock_car_signals.dart` — `MockCarSignals implements CarSignals` with `StreamController` and `emitSpeed(int)`, `emitBlinker(BlinkerState)` helpers.
- `dev/fake_car_signals.dart` — `FakeCarSignals implements CarSignals` with a controllable stream for integration tests.

## 11. ConfigStore — plain native-readable format constraint

From ADR 0003: ConfigStore must use a plain, native-readable format because the boot shim reads it before any Flutter isolate exists. `shared_preferences` on Android stores XML under the app's `shared_prefs/` directory — Kotlin can read it with standard `SharedPreferences` API. This is why Hive (Dart-only binary box) must NOT be used for ConfigStore even though nothingness uses it for its playlist.

Schema: one key per config entry, JSON-encoded string values. Kotlin boot shim reads keys it needs (HUD enabled, feature flags) synchronously at startup.

> **Confirmed on T1 (Block 0001):** `shared_preferences` namespaces every key under `flutter.`. The whole `AppConfig` is stored as one JSON string under **`flutter.zee.config`** → on-disk `{"flutter.zee.config":"{\"hudBoxOn\":true}"}`. On Android this is `shared_prefs/<package>_preferences.xml` (or the plugin's file) with the same `flutter.zee.config` key. **The native boot shim must read the key `flutter.zee.config`.**

## Risks

- riverpod_generator/riverpod_annotation are optional — if code-gen is not set up correctly (build_runner watch mode), generated files will be stale. Prefer explicit Provider declarations for service ports; use @riverpod code-gen only for derived providers where the syntax savings are large.
- ProviderContainer is intra-isolate only (ADR 0006). Both the DHU and HUD isolates have their own ProviderScope. Never pass a ProviderContainer across the isolate boundary — cross-isolate events must flow through the native relay or host channel.
- ConfigStore must NOT use Hive. Hive's binary box format is Dart-only and unreadable by the native boot shim. Use shared_preferences (XML on Android) which Kotlin can read via standard SharedPreferences API before Flutter initialises.
- flutter_hooks 0.21.3+1 is 9 months old — check compatibility with Flutter 3.44.1 before final pin. hooks_riverpod 3.3.2 was published 30 hours before this research; verify stability before adopting.
- go_router 17.3.0 is a major version (v17). Check breaking changes from previous major if migrating from an existing project. For a greenfield project this is not a risk.
- intl 0.20.2 is 16 months old. The flutter_localizations SDK package may impose a tighter intl constraint. Run flutter pub get and check for version conflicts.
- The nothingness reference project uses provider + flutter_hooks (not Riverpod). The Riverpod patterns described here are derived from ADR 0006 and standard Riverpod docs, not from nothingness source. Validate the ProviderScope.overrides injection pattern against the zee-specific two-isolate topology before committing to a deep implementation.
- VM-service isolate identity: ADR 0004:21 notes both isolates are named 'main' with the same rootLib. Every driveable surface MUST expose a whoami probe; the Feedback Loop driver builds the surface→isolateId map from it. Without this, tapByKey calls may target the wrong isolate.
- The HUD engine must be fully started before its ext.zee.* extensions are reachable. The Feedback Loop client must poll getVM until both isolates are enumerated before issuing any HUD-targeted RPC (ADR 0004:21).
- No freezed in the recommended stack — data classes use manual copyWith or Dart 3 records. If models become complex, consider adding freezed: ^3.2.5 + freezed_annotation: ^3.1.0 as dev/dependency pair. Not included by default to keep the stack lean (AGENTS.md: SLOC is a north-star metric).

## Open questions

- Should riverpod_generator (@riverpod code-gen) be used for derived providers, or are explicit Provider/StreamProvider declarations preferred for this team's readability? The generator adds build_runner complexity but reduces boilerplate for complex AsyncNotifiers.
- What is the exact JSON schema for ConfigStore's shared_preferences keys? The boot shim's Kotlin reader needs an agreed key list and value types before the ConfigStore port is implemented.
- Is go_router needed at all? The DHU touchscreen may have a simple enough navigation tree (2-3 top-level screens) that Navigator 2.0 imperative API suffices — go_router adds ~500 KB to APK. Evaluate once the screen list is finalised in REQUIREMENTS.md.
- The nothingness project uses provider 6.1.2, not Riverpod. Should the zee-power-toys project evaluate whether nothingness's ChangeNotifier + provider approach would suffice for the simpler DHU screens, reserving Riverpod complexity only for the service injection layer? ADR 0006 clearly says Riverpod is the single primary — this question is for awareness only.
- flutter_lints 6.0.0 vs very_good_analysis 10.2.0: the stricter ruleset catches more issues at the cost of more suppression comments. Given the automotive safety-relevant context, is very_good_analysis warranted?
- For T1 desktop two-engine integration, how will the second ProviderScope (HUD isolate) be bootstrapped? The dev/main_test.dart entrypoint needs to spawn two engines with separate ProviderScopes and wire the host channel relay between them.
